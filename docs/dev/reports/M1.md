## 三、首字延迟对比

同渠道、同模型的参考对比。`chat` 的首字取 Trace 的 `timing.firstTokenMs`；直连数据取本轮重跑的渠道体检，首个正文增量到达的时间。两者的提示词长度与工具定义不同，这是参考值，不是受控基准。

| 测量 | 首字或首增量 | 说明 |
|---|---|---|
| chat 第 1 轮 | 1731 毫秒 | live 三轮测试 |
| chat 第 2 轮 | 2202 毫秒 | 同上 |
| chat 第 3 轮 | 1857 毫秒 | 同上 |
| chat 中位数 | 1857 毫秒 | 三轮样本 |
| chat 均值 | 1930 毫秒 | 三轮样本 |
| 渠道体检直连 | 2045 毫秒 | 同一渠道、同一模型的第一个正文增量 |
| 验收单次抽查 | 3764 毫秒 | 模型先输出 161 个思考 token 并调用两个写入工具的一轮 |

结论：三轮对话的首字中位数比直连体检少 188 毫秒，均值少 115 毫秒；链路没有增加额外的模型往返。单次抽查的 3764 毫秒出现在思考内容较长且带工具调用的一轮，说明首字主要受模型思考长度影响。M1 的生成链路可以认为不比直接调用渠道慢，但这组数字只覆盖一个渠道和四个样本。

在 `.devloop/scratch/` 用合成角色卡发起一轮真实生成，然后用 `StoryStore` 读回该楼层的 Trace。抽查数据库与脚本在提交前删除。

| 字段 | 实测 |
|---|---|

| 上下文 | 总共 134 token；character 34、protocol 91、history 9 为 `included`；lore、state、summary、memory、director 为 `missing-slot` |

| 假设 | 实测 | 结论 |
|---|---|---|

## 八、遗留事项

- 显示视图、记忆视图、读取工具循环与后台任务都不在 M1 范围。

- `pi-agent-core` 仍只在 `spikes/pi/` 使用，运行时接入放在 M2-T14。
- bge-m3 只验证了单次调用；限流与批量稳定性留到 M2-T09。

## 九、结论

M1 的目标「原生链路稳定可用」达成：真实渠道上的 3 轮对话可以流式生成、解析块、处理结构化输出、写入楼层与 Trace；门禁与 live 测试全部通过；首字延迟在一个渠道上不高于直接调用。没有违反不变量。M1 收尾，转入 M2 的楼层树与记忆引擎。
