## 二、五轮链路

`director-acceptance.test.ts` 用假客户端跑通“计划 → 拍选择 → 注入 → 落拍 → 候选行动”：

1. 计划含一条弧线、两个序列、三个节拍；故事设置 `openingFloors` 为 0，让节拍而不是开场导演给出建议。
2. 每轮 `runChatTurn` 只发一次正文请求；导演评估没有额外请求。最后一条 user 消息以玩家原文开头，包含 `【导演】<指令>`，并以 `玩家行动优先，你可以按剧情需要调整。` 结尾。
3. 第 1 至 3 轮的指令分别包含 `beat-1`、`beat-2`、`beat-3` 的目标、起始迹象与契合点，且这些片段逐字来自计划；决策的 `signals.beat` 记录弧线、序列、节拍 id、强度与使用的契合点。
4. 每轮落拍用同一份结算请求完成：`createSettleHandler` 每次只发一次请求；提示词只在存在当前拍时出现 `当前拍：<id>（目标：<目标>）` 与 `beatCompleted` 说明。模型报告完成后写入 `director_beat_states`，下一轮解析出下一拍，第 3 拍完成后进入耗尽状态。
5. 第 4、5 轮没有当前拍：指令不含任何节拍目标，决策的 `signals.beat.beatId` 为 null；结算提示词不提 `当前拍` 与 `beatCompleted`，也不写拍状态。
6. 每轮间隙生成候选行动（一次调用，4 条行动加 1 条场景变化）；全部 25 条候选正文都不出现在任何一轮的正文请求里，候选也没有改变 head。
