## 二、指标口径

### 1. 配对判定

B1、深回合增益与偏好一致率都用同一套配对判定：

|配对结果|含义|
|---|---|
|胜|两种展示顺序都选中同一侧（续写、深回合或玩家接受侧）|
|负|两种展示顺序都选中另一侧|
|平|两种顺序都判平|
|换序不一致|两种顺序选中不同侧，或一侧判平一侧判胜负|

- 胜率 = 胜 /（胜 + 负）；平与换序不一致不计入胜率分母。
- 换序不一致比例 = 换序不一致对数 / 两种顺序都完成的对数。
- 两种顺序各判一次；同一样本同一顺序有多行时取最后一行。

### 2. 统计区间

- 所有胜率给出 Wilson 95% 区间，以配对为计数单位（不以单次判定为计数单位），`z = 1.96`：
  `lower = (p + z²/2n − z·sqrt(p(1−p)/n + z²/4n²)) / (1 + z²/n)`，`upper` 同式取加号。
- 区间下界只与 0.50 比较；计数为 0 时区间记为空，并判样本不足。

### 3. 指标定义

|指标|定义|实现|
|---|---|---|
|重复度|同一运行内相邻生成助手回复的字符 4-gram Jaccard 均值；只计内容字符（汉字、字母、数字），标点、空白与符号不参与；集合为空的对跳过|共享指标模块（R6-T01），X2 与 R6 共用同一实现|
|推进度|第 2 轮起，每条生成助手回复里未在本运行内更早生成助手回复中出现的内容字符 4-gram 占比的均值；前文不含导入历史与玩家消息|同上|
|B1 胜率|续写与历史回复的配对判定|`historical-replay` 的配对规则 + R6-T03 的批次接线|
|矛盾率|原生档探针判定里，矛盾数 /（一致数 + 矛盾数）；无法判断不计入分母，单独报告|`probe` 的取题与裁判 + R6-T02 的探针排期|
|深回合胜率|同一玩家楼层上深回合续写与快回合续写的配对判定|`deep-eval` + R6-T05 的门槛接线|
|偏好一致率|真实玩家偏好对里，两种顺序都选中玩家接受侧的配对占比|`pairwise` 汇总 + R6-T04 的配对级换算|
|成本与时延|每轮的写作非缓存请求、后台请求、输入与输出 token、Trace 首字与时延；预热与判定的请求单列|Trace 与运行记录|
|叙事质量|续写侧与对照侧的原创性、人物、节奏、对话四项 1–5 分；只报告，不作门槛|`quality`|
|运行失败率|失败轮次 / 设定轮次|运行记录|

## 三、门槛

判定结果只有三种：通过、未通过、样本不足。任何一项不是通过，都进入第四节的处理。

|编号|门槛|通过条件|样本不足的条件|
|---|---|---|---|
|G1|B1 盲测胜率|两种顺序都完成的配对至少 27 对，覆盖 3 个故事；胜率点估计高于 0.50 且 Wilson 95% 下界高于 0.50；平、换序不一致与失败合计不超过计划配对的 30%；换序不一致比例不超过 20%；裁判失败不超过判定次数的 10%|完成配对少于 27 对，或覆盖故事少于 3 个|
|G2|重复度|原生档合计不高于朴素档；任一故事的差值不超过 +0.010；每个档位至少 240 个相邻回复对|相邻回复对不足 240|
|G3|推进度|原生档合计不低于朴素档；任一故事的差值不低于 −0.020；每个档位至少 240 个推进度样本|推进度样本不足 240|
|G4|矛盾率|原生档至少 30 条可判定探针；矛盾率不高于 30%；无法判断不超过已完成探针的 50%；裁判失败不超过探针次数的 10%|可判定探针少于 30 条|
|G5|深回合增益|两种顺序都完成的配对至少 24 对；深回合胜率点估计高于 0.50 且 Wilson 95% 下界高于 0.50；平、换序不一致与失败合计不超过计划配对的 30%；深回合失败率不高于 10%|完成配对少于 24 对|
|G6|偏好一致率（条件门槛）|两种顺序都完成的真实偏好配对至少 30 对时：一致率不低于 60% 且 Wilson 95% 下界高于 0.50|少于 30 对时记为未证实，不计为未通过，也不计入通过|

- G1 的 B1 是整个样本对历史回复的胜率。历史回复来自不同家族时，同时报告同家族子集与模型清单；同家族子集不单独设门槛，因为现有 3 个对话里同家族样本不足 20 对。
- G2 与 G3 的合计值是三个故事均值的再平均；每个故事的分项也写入报告。
- G4 的探针从原生档当前路径的台账事实生成，问的是事实本身；朴素档没有台账，不参与该项。
- G5 在预热后的副本上运行；深回合与快回合都使用同一模板、同一预算与同一玩家楼层。
- R6 通过：G1 至 G5 全部通过，且 G6 通过或未证实。

## 四、判定与改进循环

1. R6-T06 跑完 C1 与 C2，R6-T05 跑完 C3，R6-T99 用门槛判定库逐项判定，结果写入 `docs/dev/reports/R6.md` 与 `docs/dev/SCOREBOARD.md`。
2. 任一项未通过或样本不足：R6-T99 写 `docs/dev/R6-ROUND-<n>.md`（n 为评测轮次），按失败项生成改进任务，编号 `R6-F<n>-a`、`.b`……，每个失败项最多 3 个任务。
3. 每个改进任务必须写清：失败的编号与数字（点估计、区间、样本数）、至少 3 条来自私有数据的失败依据（仓库文档只写统计描述，不写原文）、改动假设、最小改动范围、重跑命令与预期变化。一次只改一个方面，避免无法归因。
4. 改进后按同一门槛、同一分支点、同一串玩家消息、同一种子重新运行；最多三轮评测（第 1 轮为初次判定，第 2、3 轮为改进后的重新判定）。第 3 轮仍未通过时，把每项的差距与已尝试的改动写进 `docs/dev/HUMAN.md`，R6-T99 结果为 `BLOCKED`。
5. 样本不足的项同样进入改进任务，任务目标是补足样本或修好取题、判定链路，不改门槛。
6. B1、B0 与 G6 的样本不足时，不通过降低门槛或换故事来凑数。

## 五、B2 申请模板与样本上限

B2 只在 G1 未通过、且已完成至少一轮改进后使用；每次使用前在 `docs/dev/HUMAN.md` 写一条申请，得到明确确认才执行。

申请必须包含：

|字段|内容|
|---|---|
|对应门槛|G1 与当前轮次|
|目的|说明 B1 为什么不够（例如需要玩家本机 ST 的真实生成做对照）|
|样本|分支点数量、每个分支点的生成次数；单次合计不超过 60 次（I14）|
|模型与渠道|写作模型、本地 ST 的配置与插件清单；不读取凭证|
|时长与成本|预计分钟数、token 上限、是否占用玩家额度|
|数据|原始数据保存目录（`eval-private/` 下）、仓库报告只写哪些聚合字段|
|中断处理|超时、失败、取消后的恢复方式与可重复命令|
|审批|等待人类在 HUMAN.md 回复；没有回复时不执行|

- 上限：每次申请最多生成 60 次；每个评测轮次最多使用 1 次；R6 全程最多 2 次。
- B2 的判定沿用 G1 的配对口径，不与 B1 样本混合计算。
