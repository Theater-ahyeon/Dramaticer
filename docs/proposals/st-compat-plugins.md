# ST 生态兼容插件套件提案（2026-11-07，已获人类确认）

> 人类要求：做几个**完美兼容 SillyTavern 全部生态**的插件，在 Dramaticer 里可以**按需选用**。
> 这份提案**取代**此前"ST 兼容只做到够用、主动放弃长尾"的说法：长尾兼容不再放弃，而是全部做进**可选插件**；`core` 仍然不出现任何 ST 概念（I1 不变）。

## 〇、"完美兼容"怎么定义，怎么验证

"完美"不能靠口头声明，必须可以测量。每个插件都有**一致性测试**：

| 层面 | 验收方式 |
|---|---|
| **Prompt 一致** | 在仓库内（`eval-private/st-sandbox/`）复制一份玩家的 SillyTavern 程序和数据，把它的 API 地址指向一个**本地录制服务**（只记录请求、不调用任何模型，**零额度**）。用玩家的 58 个预设 × 卡片 × 对话片段驱动 ST 生成，录下 ST 真实组装出的请求，和 Dramaticer 在同样输入下组装的结果**逐条比对**。目标：受支持的功能 100% 一致；不一致的地方逐条列出原因 |
| **API 覆盖** | 以酒馆助手（JS-Slash-Runner）、MVU 的公开类型定义为准，统计已实现函数的覆盖率，每个函数都要有测试 |
| ~~扩展可用~~ | 取消：ST 前端扩展不在兼容范围内（见 P-E） |
| **导入无损** | 卡、世界书、预设、对话**导入**时不丢信息（不认识的字段原样保存在插件自己的数据里）。**导出到 ST 只尽力而为，原生数据不迁就 ST 的格式** |

**原始安装目录只读**：`D:\SillyTavern\` 下的东西一律不改；所有试验都在仓库内的副本上进行。一致性测试**不调用任何模型**，不消耗玩家的 ST 额度（I14）。

## 一、插件清单（每个都可以单独启用）

### P-A `st-content`：内容与 prompt 组装（MIT）
- 角色卡 V1/V2/V3（PNG/JSON）、群聊卡、人设、作者注释
- **世界书的完整激活语义**：主次关键词与逻辑（AND/NOT 各种组合）、正则关键词、递归、`sticky`/`cooldown`/`delay` 等定时效果、分组与组内权重、概率、扫描深度、位置/深度/角色、outlet 等
- **预设**：`prompt_order`、深度注入、角色、预填充、续写预填充、squash 系统消息、各种 format 字段、采样参数
- **完整宏引擎**：ST 的全部宏，包括变量类（局部、全局）、`random`/`pick`/`roll`、时间类、`{{// }}`、`trim`、outlet 等
- **完整正则语义**：作用范围、只影响显示或 prompt、深度、trim strings、宏替换、编辑时执行
- 对话的导入导出（jsonl），包括 swipe 和插件数据
- 实现方式：把 ST 内容**转换成 Dramaticer 的原生模板和槽位**，再由组装器生成请求；凡是原生模型表达不了的，在插件里按 ST 的语义处理

### P-B `st-ejs`：Prompt Template（EJS）兼容（MIT）
- 世界书条目和预设里的 EJS 模板，包括 `getvar`/`setvar` 等函数、装饰器、激活正则和世界书条目的能力
- 在沙箱里执行

### P-C `st-mvu`：MVU / MagVarUpdate / zod schema 兼容（MIT）
- `initvar`、`<UpdateVariable>`、JSONPatch、`[值, 说明]`、`$meta`（strictSet、extensible、模板）、zod schema 校验
- **映射到台账**：MVU 变量成为台账里的一个命名空间；更新指令交给结算器校验和修复（I12），并借鉴故事神谕诊断模式里的自动纠错

### P-D `st-helper-host`：酒馆助手宿主（MIT）
- 执行酒馆助手脚本、角色卡内脚本、HTML 状态栏和开场页
- 运行在**沙箱 iframe** 里，提供与酒馆助手 API 对齐的接口：变量读写、事件监听、`triggerSlash`/STscript、生成、读取消息、修改消息……
- **修改消息**一律映射成新建楼层或新的 swipe，不修改原文（I4）
- 参考：DSH Tavern 已经实现过酒馆助手脚本的宿主适配，证明可行

### ~~P-E `st-classic-ui`：经典界面~~（**人类 2026-11-07 决定：不做**）

> 人类决定：**ST 前端扩展不需要完美兼容**，原生数据也**不需要迁就 ST 的格式**。所以这个插件取消，不排入路线。下面的原文只作为记录保留。前端扩展的主要用途（记忆、规划、状态修复、生图）由 Dramaticer 的原生功能覆盖；酒馆助手脚本、HTML 状态栏和开场页仍由 P-D 支持。

（原文如下）
- 这是"完美兼容全部前端扩展"的唯一途径：**Dramaticer 实现 SillyTavern 的后端 HTTP 接口**，让真正的 SillyTavern 前端直接跑在 Dramaticer 上面。这样**所有 ST 前端扩展原样可用**（柏宝书、故事神谕、LittleWhiteBox 等），而生成请求、存储和后台工作全部经过 Dramaticer 的 harness。
- 快回合和深回合通过模型名切换（例如 `dramaticer-deep/…`）。
- **存储映射**：ST 每次保存的是整份聊天数组；后端把它和楼层树做差异比较，追加新楼层；编辑就变成新的兄弟节点。原文不可修改（I4）的约束不变。
- **ST 前端代码不打包进 Dramaticer**：由用户指定自己本机的 SillyTavern 安装，或者由插件在首次启用时从上游下载一个固定的版本。
- **许可证**：SillyTavern 是 AGPL-3.0，所以这个插件**单独成包，采用 AGPL-3.0**；Dramaticer 的 core 和其他插件保持 MIT。
- 参考：TauriTavern 就是"保留 ST 前端 + 重写后端"，证明可行；它的文档可以当作接口规格来参考。

## 二、和插件系统的关系、执行顺序

- 这些都是 `docs/proposals/plugins.md` 里所说的**代码插件**，依赖插件内核改造（P2）完成。
- 原来的"兼容线"（C-T00）**由这套插件取代**。
- 顺序：**P-A → P-C → P-B → P-D**（P-E 已取消）。P-A 是其他插件的基础；P-C 直接影响台账。
- 每个插件都要先搭好一致性测试，再写实现（先让测试变红，再让它变绿）。

## 二·五、共存规则：兼容插件不得削弱原生功能

架构上（I15）兼容插件改不了 core；但**运行时**仍可能互相干扰，所以必须遵守以下规则，并且用测试来证明：

| 风险 | 规则 |
|---|---|
| ST 的世界书和预设内容很大，挤掉记忆、台账、导演的上下文空间 | ST 内容以槽位的形式进入**原生的预算分配器**，按原生的优先级裁剪（用户意志 > 人物关系 > 未兑现线索 > ……）；Trace 里分开显示 ST 内容和原生内容各占多少 token |
| 预设里自带的思维链、总结、规划指令和写作契约、导演建议互相冲突 | 写作契约始终放在离生成最近的位置；导入时识别预设里的"总结类"和"规划类"条目，提示用户关闭，或者让原生功能接管 |
| 卡的 MVU 变量和台账各管一套 | MVU 是台账里的一个命名空间（P-C），两者是同一套数据，不是两套 |
| 酒馆助手脚本自己调用模型（比如卡自带的总结脚本），破坏"每轮一次主调用"（I6） | 脚本发起的生成一律作为**后台任务**执行，走后台渠道池，不进入回合内；在 Trace 里单独计数 |
| 脚本或正则修改变量和消息 | 变量写入经过结算器（I12）；修改消息只能变成新楼层（I4） |
| "只影响 prompt"的正则误删 Dramaticer 注入的内容 | ST 正则、宏和 EJS **只作用于来自 ST 的内容**，不碰 harness 槽位（记忆、台账、导演、写作契约） |
| 宏、EJS、世界书递归激活拖慢回合 | 计入回合内的时间预算，超时记录到 Trace |

**共存验收**（每个兼容插件都必须通过）：用同一批卡，分别在**开启和关闭**该插件的情况下跑评测，原生指标（矛盾率、编造回忆率、盲测胜率、首字延迟）**不能因为开启插件而明显变差**；变差了就修插件，不改 core。

## 三、对其他提案的修正

- v3 和 F0-T100 里关于"放弃清单"的说法改为：**不放弃 ST 的任何生态功能，全部做进可选的兼容插件**；core 保持干净。
- 新增 ADR：允许开发 agent 把本地 SillyTavern 程序和数据**复制到仓库内**运行，指向本地录制服务做一致性测试；不得修改原安装目录，不得调用任何模型。
