## 一、数据对路线的含义

1. **开局问题至少和遗忘一样突出。** 重 roll 最集中的是开局 10 楼（0.2），短对话又常在重 roll 后结束。在 F0 证明之前，“遗忘与串戏”不能默认是第一主因。
2. **间隙很短。** 四分之一的间隙不到 60 秒，后台渠道实测约 2.7 次/分钟（HANDOFF）。所以下一轮必须用到的间隙工作，每回合最多只能有约 1 次调用。v2 设计在间隙里排了 6–10 类任务，按现在的拆法一定会积压。
3. **回复长度与默认值不匹配。** 回复 P50 约 2.3K token，默认 `maxTokens` 1024 会系统性截断。块协议的 prompt 视图（把状态栏、变量更新从历史里去掉）可能比检索更早见到效果：历史里约 65% 的字符是标签块。
4. **只要给出格式，模型就会写结构化块。** I13 不变（不强制），但原生模板应该提供可选的块格式说明。结算器应先解析模型已经写好的块，只在缺失时调用模型补写，这样能省掉相当一部分后台调用。
5. **玩家输入很短**（P50 13 token），选项和交互输入又是现成的高频习惯。候选行动有现成的需求；用户意志的捕获来源很少，不值得单独做一个间隙任务。
6. **生图是高频需求**（85% 的对话带生图插件元数据），排在 R7 之后太晚。
7. **B1 历史回放主要是在和 Gemini Pro 级模型比。** F0 和 R2 的写作模型是 DeepSeek V4.1 Flash，B1 的胜负会混入模型差异。
8. **深回合的价值在草稿和自检，不在检索。** TauriTavern 的 agent 只有 3% 的工具调用是主动查聊天记录，这支持“被动注入保底”。失败率 23%、协议漂移 49% 说明可靠性是深回合的主要风险。时长 P50 66 秒，和现有生成耗时 P50 50 秒相近，玩家可以接受。

## 二、A 设计修订（直接采纳，不改目标与范围）

### A1 F0 的修订（在 F0-T03 运行之前生效）
- **F0-T02 按楼层深度分层抽样**：1–10 楼、11–50 楼、51 楼以上各约三分之一，报告给出分层后的原因分布。另外单列“最后一楼被重 roll 后对话结束”的子集。已完成的样本保留，按层补齐。
- **F0-T03 先登记门槛再运行**：报告里先写判定规则——交换顺序后与玩家选择的一致率 ≥ 65%、且位置偏差 ≤ 10 个百分点，才把 LLM 裁判用于偏好判断；达不到时，R2 的裁判只用于有台账可对照的矛盾与遗忘判定，偏好改用玩家的选择数据。
- **F0-T04**：全文 token 先剔除标签块再估算，“全部正文”组同时报告含标签与不含标签两种口径。F0 固定只用一个模型，所以裁判结论注明“同模型自评”，不能当作 R2 的裁判口径。
- 把 0.1–0.6 的统计并入 `scripts/f0-corpus.mjs` 与 `F0-corpus.md`，保证可复现。

### A2 结算时序：投机结算当前楼层
- “确认”只决定哪些结果算数，不决定什么时候开始算。回复落定后就对 head 结算；结果绑定在节点上，swipe 产生的新节点各自结算，被放弃的节点结果保留但不在当前路径上。
- R1-T02 的“已确认、尚未结算”改为“已落定、尚未结算”。现场分析与世界书预筛读投机结算后的台账，不再落后一楼。

### A3 间隙合并调用与容量预算
- 新增后台任务 `gap_pass`：每个回合一次结构化调用，同时产出结算 diff、现场分析、用户意志与修订候选，事件也可以一起产出。原来的任务类型保留为输出里的分段和各自的校验器，不改存储。
- 按“下一轮要不要用”分两档：下一轮要用的（`gap_pass`、世界书预筛）优先；可以延后的（章节压缩、事件回填、导演规划、NPC 议程）只在长间隙（超过 P75）或会话结束后运行。
- 队列里过期的任务（head 已经变化）直接丢弃。Trace 和自动试玩报告新增“间隙未完成率”，即下一轮开始时关键间隙工作没有完成的比例。

### A4 结算器先用模型写好的块
- 输入顺序：本楼层已有的结构化写入（`state_update`、原生块；兼容插件开启时还有 MVU 的 `UpdateVariable`/`JSONPatch` 与 ACU 表格编辑）→ 校验与修复 → 只对缺失的部分调用模型。
- 原生模板附带可选的块格式说明，由卡作者或玩家开启，不强制（I13）。

### A5 台账写入的实体解析与冲突处理
- 写入前把人物、地点、物品的 id 对照实体与别名表规范化；不认识的实体先放进“候选实体”，在同一窗口里出现两次以上或被模型写入时才建档。
- 每条结算事实带置信度。与最近 N 楼原文冲突的结算事实不覆盖已有事实，生成待审记录（复用 R1-T07.a 的变更卡）。
- `knowledge` 的事实键改为事实 id（指向事件或线索），不用整句文本当键，以便去重。

### A6 生成长度默认值
- `maxTokens` 默认值改为 4096 或渠道上限中较小的一个；截断检测结果写进 Trace，自动试玩报告统计截断率。

### A7 裁判与写作“不同渠道”的判据
- R1-T01.b 改为比较模型家族（由模型名映射；映射不到时比较完整模型名），不比较 `baseUrl`：所有模型都经过同一个本地网关，`baseUrl` 相同不代表是同一个模型。

### A8 基线口径
- 主对照是同一写作模型下的 B0 与 native。B1 历史回放的报告里必须标出历史回复所用的模型；能找到同模型样本时用同模型的子集，找不到时 B1 只作为“相对现状”的参考，不作为门槛。

### A9 深回合（并入 R3-T00）
- 容忍协议漂移：模型没有调用提交工具、直接输出了正文时，把它当作草稿接住，而不是判失败（TauriTavern 有一半的运行需要这样处理）。
- 验收增加运行失败率、漂移率与时长分布；目标是失败率明显低于 23%。

### A10 兼容插件补充规则（补充 ADR-0040）
- **两种模式**：“忠实模式”关闭全部原生功能，用于 C-T01 的一致性比对，目标是 100% 一致；“共存模式”按 ADR-0040 执行，不做一致性比对，只做开关对照评测。
- **读到自己刚写入的值**：脚本写变量后立刻读取，要读到待结算的值；这一层是插件内的临时视图，结算后以台账为准（I12）。
- **修改消息分两类**：改正文 → 新 swipe（I4）；只改显示或元数据（状态栏刷新这类）→ 写进插件自己的显示状态，不新建节点，以免节点暴增。
- **作用范围**：导入对话的 history 槽位属于 ST 内容，ST 正则可以作用于它；记忆、台账、导演、写作契约等 harness 槽位不受影响。
- **净室规则**：ST 是 AGPL-3.0。实现 `st-content` 等插件时只以录制下来的行为和测试作为规格，不移植或改写 ST 源码；其他上游项目（酒馆助手、MVU 等）在 C-T01 先逐个确认许可证，结果写进 DEPENDENCIES。
- **执行隔离**：EJS 与脚本在 worker 或 iframe 里执行，不把 `node:vm` 当作安全边界；脚本发起的生成按卡限流并计入后台预算。

### A11 文档一致性
- DESIGN §9 最后一条（“不支持酒馆助手脚本、EJS”）和 §16（“运行酒馆助手脚本，或模拟 ST 内部 API”）已被 ADR-0038 取代，下一个会话先在原处加上取代标注，F0-T100 再整体改写。
- TASKS 里已完成的里程碑（M0–M4、D、R0 的已完成项）移到 `docs/dev/TASKS-archive.md`，减少每个会话开头读取的篇幅。

## 三、B 路线修订（只调整顺序，不缩小范围；交 F0-T100 按 F0 数据定序）

1. **纵向切片提前**：先做出 R1 的最小集（结算器、`gap_pass`、块的 prompt 视图、A6），然后是 R3 快回合、R5 的最小界面（聊天、swipe、台账只读面板、图片与选项块显示），再接自动试玩。父子分块、重排序、八段式压缩和世界书预筛，等 B0 对 native 的长对话评测显示确实存在遗忘问题后再做（任务全部保留）。
2. **开局质量作为主菜候选**：例如开场导演、首楼多候选、前 10 楼的导演强度。是否列为主菜，由 F0-T02 的分层结果决定。
3. **生图提前**：M6 的第一批（ComfyUI 与 `illustrate` 块显示）排到最小界面之后，不再放在 R7 之后。
4. **插件内核 P2 排在 R5 之后**：等内置模块接口稳定后再抽象，避免重写两遍。P1 技术验证可以提前做。
5. **兼容插件按使用频度排子集**：P-A 先做世界书（包括定时效果）、预设、宏、正则；P-C（MVU）与 P-A 同期，因为台账导入依赖它；EJS 与酒馆助手宿主随后做。全部范围保留。
6. **公开合成基准提前到 R2**：3 个私有对话的样本量撑不起门槛判断。

## 四、可能的问题与应对

| 风险 | 应对 |
|---|---|
| 0.2 的开局重 roll 可能来自玩家“试卡”，而不是不满意 | F0-T02 的归因里，“只是想看别的写法”单独统计 |
| 0.3 的标签占比用正则粗略估算，嵌套标签会重复计数 | 只当方向性证据；F0 并入脚本时改用 core 的块解析器统计 |
| 0.7 只有 53 次运行，而且是另一个产品的协议 | 只作为风险提示，R3 用自己的数据验收 |
| `gap_pass` 把几个任务合并成一次调用，单项质量可能下降 | 合并调用与拆开调用在同一批楼层上对比结算准确率，结论写 ADR |
| 投机结算增加了被放弃的 swipe 的结算成本 | 结算只在玩家停留在该节点超过一定时间后才开始（或者在下一轮发送时补算），具体由实测决定 |
