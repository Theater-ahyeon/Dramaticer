# Dramaticer 插件系统提案（2026-11-07，已获人类确认，并入 v3）

> 目标：让社区可以自己定制和分享插件，成为 Dramaticer 作为独立产品的生态护城河。
> 参考：Cordis（Koishi 生态的元框架，MIT，作者 Shigma；DSH 用的是它的分支 `@deepseek-ai/cordis` 4.0.5）、DSH 的"profile = 有序的插件包补丁层"、TauriTavern 的 `SKILL.md`、ST 的卡片附带世界书的生态经验。

## 一、借鉴 Cordis 的核心概念

| 概念 | 在 Dramaticer 里的含义 |
|---|---|
| **Context**（上下文对象） | 插件拿到的唯一入口；通过它注册钩子、提供服务、访问服务 |
| **插件** = 函数、类或对象，带 `name`、`Config`（配置 schema，加载前先校验）、`inject`（依赖的服务；依赖不可用时插件不加载）、`provide`（提供的服务） | 同上 |
| **生命周期与副作用自动回收** | 插件注册的钩子、定时器、后台任务在卸载时自动清理，支持热重载 |
| **事件分发模式**：emit / parallel / serial / bail / waterfall | 用来定义各个扩展点的语义（见第二节） |
| **服务**：插件之间通过服务名互相依赖，可以替换实现 | 比如"记忆检索"是一个服务，社区可以用别的实现替换它 |
| **Profile = 有序的插件包补丁层**（DSH） | "玩法包"：一组插件加配置；用户在上面叠加自己的覆盖 |

**吃自己的狗粮**：记忆、台账结算器、Director 机制、块类型、上下文槽位这些内置功能，本身也按插件来实现。这样可以保证插件 API 足够用，也让社区能直接替换任何一个内置模块。

**是直接依赖 Cordis，还是自己实现一个精简版**：先做技术验证再决定（见第六节）。无论选哪种，**对外暴露的 API 都是 Dramaticer 自己定义的类型**，避免被上游版本变动绑死。

## 二、扩展点（社区可以插手的地方）

| 扩展点 | 分发模式 | 所在位置 | 约束 |
|---|---|---|---|
| 上下文槽位提供者 | parallel 收集 | 回合内（热路径） | 有时间预算，Trace 记录耗时 |
| 组装后的请求改写 | waterfall | 回合内 | 有时间预算；不能删除写作契约 |
| 台账 schema 类型与校验规则（比如修仙境界、好感度规则） | 注册 | 结算器 | 写入必须经过结算器（I12） |
| 台账变更否决或修正 | bail / waterfall | 结算器 | 同上 |
| Director 机制（实时选择） | 注册 | 回合内 | **必须是同步纯函数，不调用模型**（I9） |
| 剧情方案、剧情小品的来源 | 注册 | 间隙里的后台 | 可以调用模型 |
| 后台任务类型（抽取、规划、分析……） | 注册 | 间隙里的后台 | 走后台渠道池和限速（I11） |
| 块类型（标签 + 显示渲染器 + 上下文策略 + 语义处理） | 注册 | 解析器、界面 | 渲染在沙箱 iframe 里 |
| 工具（深回合和助手可用） | 注册 | 深回合、助手 | 声明权限级别（只读 / 确认 / 自动） |
| 模型渠道适配器、生图后端 | 服务 | 模型层 | — |
| 导入器和导出器 | 注册 | 导入导出 | — |
| 界面面板和小组件 | 注册 | Web | 沙箱 iframe，通过受控接口通信 |
| 评测指标和裁判 | 注册 | 评测 | — |
| 回合生命周期事件（回合开始、楼层提交、分支切换……） | emit / serial | 各处 | 只读通知，或者在限定范围内修改 |

**插件 API 不提供任何修改楼层原文的途径（I4）。**

## 三、两档插件：声明式优先

| 档位 | 内容 | 安全性 | 分发方式 |
|---|---|---|---|
| **声明式插件**（主力） | 台账 schema、剧情小品、原生模板、块渲染器（沙箱里的 HTML 模板）、`SKILL.md` 技能、导演配置、事件池 | 只有数据，没有代码，安全 | **可以直接打包进角色卡**（`extensions.dramaticer`），像 ST 的卡附带世界书一样 |
| **代码插件** | 任意 JS，用 Context API 注册扩展点 | 需要明确授权 | npm、git、zip 安装；带权限清单（网络、文件、模型调用、台账写入……），安装时展示；默认运行在 worker 隔离环境里 |

社区的大部分价值可以用声明式插件实现，门槛也低（卡作者就能写）。代码插件留给真正需要它的人。

## 四、清单、玩法包与卡片依赖

- **插件清单**：名称、版本、兼容的 Dramaticer 版本范围、`inject` 和 `provide`、配置 schema、权限、档位。
- **玩法包**：一组插件加配置（例如"修仙跑团包""恋爱养成包"）；用户在上面叠加自己的覆盖（借鉴 DSH 的补丁层）。
- **卡片可以声明依赖**：卡里写明需要或推荐哪些插件和玩法包，导入时提示安装。这解决了 ST 生态里"这张卡要装某个扩展才能正常用，但没人告诉你"的问题。
- **按故事启用**：每个故事可以单独开关插件和覆盖配置；分支之间共享同一套配置。

## 五、插件市场（公开发布之前做）

在应用内浏览、搜索、安装和更新；显示权限和档位；支持从 git 地址安装。**发布、上架等对外操作仍然遵守发布边界，由人类执行。**

## 六、执行顺序

| 阶段 | 内容 | 时机 |
|---|---|---|
| P1 | 技术验证：直接依赖 Cordis（上游的 MIT 版本）vs 自己实现精简版，比较类型体验、热重载、依赖管理、包体积，写 ADR | v3 合并之后马上做 |
| P2 | 内核改造：引入 Context 和插件注册表，把内置模块（槽位、Director 机制、块类型、后台任务、工具）逐个改成插件形式，**每改一个都保持门禁和评测不退化** | 和 R3 并行或紧随其后 |
| P3 | 声明式插件格式定稿；卡片可以打包声明式插件；导入时提示依赖 | 内核改造之后 |
| P4 | 代码插件：权限清单、worker 隔离、安装与更新；插件开发文档和示例插件 | 公开 alpha 之前 |
| P5 | 应用内插件市场 | 公开 alpha |

## 七、新增不变量（合并时写进 DESIGN；AGENTS.md 由人类决定是否加入）

- 插件不能修改楼层原文，状态写入必须经过结算器，实时导演选择必须是纯函数（I4、I9、I12 同样约束插件）。
- 回合内（热路径）的插件钩子有时间预算，超时就跳过并记录到 Trace。
- 代码插件的权限必须声明，并在安装时展示给用户。
