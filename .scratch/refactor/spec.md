# 规格：MVP 收口与工程整理（`refactor`）

> 来源：2026-11-19 人工会话的全量架构审查。人类要求「先做完整 MVP，再慢慢优化」，并允许大改。设计见 `docs/DESIGN.md` v1.0 的 §15.2（MVP 定义）与 §15.3（工程整理）。

## 问题

1. **默认设置没有用上 v4**（已由 01 修复）：新故事用的是旧导演 `mechanisms`，自动记录默认关闭；功能页 18 个开关里运行时只读 3 个，页面显示的不是实际运行的。
2. **大文件拖慢每一次修改**：`core/src/store/story-store.ts` 单文件 11,958 行、276 个方法、86 个文件引用它；`server/src/routes.ts` 3,675 行。agent 每次改存储或接口都要在这两个文件里搜索和分段读取，冲突也集中在这里。
3. **包边界与职责不符**：`st-compat` 共约 6.9 万行，其中 `evalset/` 约 3.96 万行、`st-bench/` 约 6 千行是评测工具，不是酒馆兼容。
4. **未胜出的实验仍在主路径上**：X1 的 `wiki`、`temporal_graph`（ADR-0130），X2 的 `bits`（ADR-0134）与 v3 的 `mechanisms` 都有开关与分支代码，测试组合随之相乘。
5. **后台渠道没有真正的保底**：`bg-fallback` 走同一个 `bg` 渠道；额度耗尽时（HUMAN-19）结算、记忆、导演全部停摆，界面上看不出来。

## 原则

- MVP 相关的工单（01–04）先做；纯整理（05–08）排在 MVP 之后，除非它挡住了 MVP 的工作。
- 整理类工单**不改外部行为**：存储格式、接口路径、协议类型、Trace 字段都不变；每一步都能单独回滚。
- 每张工单结束都跑 `pnpm check`；动到 server 或 web 的跑 `pnpm e2e`。

## 不做

- 不重写存储层或换 ORM；不改迁移历史。
- 不为整理新增运行时依赖。
- 不在这批工单里改记忆、导演的算法。
